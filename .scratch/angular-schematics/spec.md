# Angular Schematics 功能需求设计

Status: resolved

Type: task

Labels: ready-for-agent

## Problem Statement

组件库使用者目前需要手动安装库及其依赖、配置 OpenLayers 全局样式，并参考文档编写地图组件。接入步骤分散，容易遗漏样式、地图高度或依赖版本要求。

已有应用的使用者希望通过 Angular
CLI 快速完成接入，并自主决定是否添加地图示例。新应用的使用者希望直接生成一个能够启动、测试和构建的地图应用，减少重复搭建工作。

维护者需要遵循 Angular 官方 Schematics 机制，将安装和生成能力纳入现有构建、测试及发布流程。Schematics 源码应作为独立内部项目管理，用户仍通过组件库本身的包名使用这些能力。

## Solution

提供两个公开入口：

- `ng add @workletjs/ngx-openlayers`：完成目标应用的依赖和样式接入，并询问是否生成地图示例。
- `ng generate @workletjs/ngx-openlayers:application <name>`：在现有 Angular
  workspace 中创建完整地图应用。

安装命令默认不生成示例。用户确认后，生成基础 OSM 地图组件，并将其作为懒加载页面接入指定路由。组件名称和路由允许自定义，既有应用内容不被覆盖。

地图应用模板采用固定的现代 Angular 配置，启动后进入地图页。两种入口共享地图内容和基础接入规则。

首版支持 Angular CLI 22.2.x 标准 workspace。内部 Nx 项目名称为 `schematics`，私有包名称为
`@workletjs/schematics`；其编译产物随 `@workletjs/ngx-openlayers` 一起发布。

### 使用示例

```bash
ng add @workletjs/ngx-openlayers --project existing-app
ng add @workletjs/ngx-openlayers --project existing-app --example --example-name demo-map --route demo-map
ng generate @workletjs/ngx-openlayers:application map-app
```

### 命令选项

| 选项                         | 适用命令    | 行为                                                        |
| ---------------------------- | ----------- | ----------------------------------------------------------- |
| `<name>`                     | application | 必填的新应用名称，沿用官方应用生成器的校验。                |
| `--project`                  | ng add      | 明确指定已有目标应用；缺省时从 CLI 当前项目或唯一应用确定。 |
| `--example` / `--no-example` | ng add      | 控制是否生成并接入地图示例；未指定时交互确认，默认否。      |
| `--example-name`             | 两者        | 地图示例组件名称，默认 `map-example`。                      |
| `--route`                    | 两者        | 地图示例路由，默认 `map`，对应访问地址 `/map`。             |
| `--project-root`             | application | 新应用根目录，缺省时沿用官方生成器的位置约定。              |
| `--skip-install`             | 两者        | 跳过 schematic 后续依赖安装任务。                           |

在 ng add 中，示例名称和路由仅在启用示例时生效；关闭示例不检查宿主路由条件。

## User Stories

1. 作为组件库使用者，我希望通过 ng add 接入组件库，以便减少手动配置步骤。
2. 作为组件库使用者，我希望命令支持当前库兼容的 Angular CLI workspace，以便明确接入环境要求。
3. 作为组件库使用者，我希望组件库被保存为应用依赖，以便应用安装和构建时能够使用它。
4. 作为组件库使用者，我希望安装要求来自本次安装版本的 peerDependencies，以便避免使用错误的历史版本要求。
5. 作为组件库使用者，我希望兼容的已有依赖声明保持原样，以便保留项目已有版本策略。
6. 作为组件库使用者，我希望缺少的 CDK 和 OpenLayers 依赖得到补齐，以便直接使用组件库。
7. 作为组件库使用者，我希望不兼容依赖产生明确错误，以便在接入前解决版本问题。
8. 作为组件库使用者，我希望命令不自动升级或降级 Angular，以便控制应用升级范围。
9. 作为使用本地依赖或版本标签的开发者，我希望通过已安装版本验证兼容性，以便保留既有依赖来源。
10. 作为组件库使用者，我希望自动配置 OpenLayers 全局样式，以便地图控件正常显示。

## Implementation Decisions

- 采用 Angular 官方 Schematics collection、JSON
  schema、TypeScript 选项接口、Rule/Tree 和文件模板机制。源码按已确认的内部项目布局组织，不改变官方的集合发现和随库发布机制。
- 公开集合仅提供 ng-add 和 application；地图示例生成作为内部共享规则，不增加独立公开组件生成命令。
- 内部 Nx 项目名称固定为 schematics，私有包名称固定为 @workletjs/schematics，设置 private，并从 Nx
  Release 的通配项目集合中显式排除，不单独发布或参与版本管理。
- 主库声明对内部项目的 Nx 构建依赖，用于构建调度、affected 分析和缓存失效；内部项目不导入主库实现或依赖主库构建，模板中的公开包导入字符串不构成反向构建依赖。
- 集合编译产物随组件库发布。组件库声明集合入口、安装保存类型和所有直接执行期依赖，不依赖私有包在用户环境中存在，也不依赖 CLI 偶然提供的传递依赖。
- 安装命令接受 project、example、exampleName、route、skipInstall。应用生成命令接受必填应用名称及 projectRoot、exampleName、route、skipInstall；命令行选项使用 Angular
  CLI 对应的连字符形式。
- example 使用原生布尔确认提示，默认 false；显式参数不重复提示，非交互运行采用 false。关闭示例时跳过全部路由检查，不额外询问示例名称。
- 示例名称默认 map-example，路由默认 map。两者均由小写字母开头，后续为小写字母或数字，可用单个连字符分隔非空片段；不接受嵌套路径、参数、通配符、查询字符串或路径穿越。
- 目标项目优先使用显式参数，其次使用 CLI 当前项目或唯一应用；歧义时列出候选并要求指定，不选择列表中的首个项目。目标必须是应用。
- 版本要求来自本次安装包已解析的 peerDependencies，不能直接使用未解析的 workspace
  catalog 引用。保留兼容声明及其所在依赖区段，只补齐缺少的 CDK、OpenLayers，不自动安装或升级 Angular 核心来修复无效宿主。
- 普通版本范围需与库要求相交，已安装版本存在时还需满足库要求。非 semver 声明仅在已安装版本可以验证时接受，否则提示先完成安装或修正声明。冲突说明包含依赖名称、声明、可取得的已安装版本及所需范围。
- 全局样式接入同时处理基础构建选项和显式覆盖样式的 configuration，识别字符串和对象形式，避免重复并保持用户样式的相对顺序；新增 OpenLayers 样式置于用户全局样式之前。
- 现代 unit-test target 继承构建配置，不向其添加不支持的样式属性。
- 地图示例通过公开 secondary entry
  points 直接导入地图、视图、瓦片图层和 OSM 数据源组件，不增加 Material、Tailwind 或额外 bootstrap
  provider。
- 地图默认中心为
  [0,0]，缩放为 2，高度为 400px，允许键盘聚焦。沿用组件及 OSM 数据源的默认控件、交互和归属显示。
- 自动地图示例接入仅支持 standalone 应用，要求已有 Router 和根组件主路由出口；不自动创建 Router、添加出口、替换现有首页或改写根模板。
- 根据实际 bootstrap、应用配置和模板引用定位接入位置，兼容标准 CLI 的不同文件命名方式，不依赖约定文件名猜测目标。
- 使用 TypeScript
  AST 分析配置，使用 Angular 模板解析器确认根组件实际存在主路由出口。支持内联数组、同文件变量及直接相对导入的静态路由数组。
- 无法安全分析的动态配置、数组展开、路径别名或间接配置组合明确报错，不使用字符串替换猜测路由位置。
- 新增懒加载路由位于根数组首位，保留既有路由之间的相对顺序；检查根级及静态空路径分组下的同路径冲突，不覆盖既有路由。
- 修改 Tree 前完成项目、依赖、路由条件和文件冲突检查。错误信息说明原因及处理方式，不静默降级为未接入的组件。
- 重复执行时，若路由、组件引用和完整文件对应同一地图示例，则保持现状并保留用户修改；其他冲突或不完整状态报错。同名组件改用不同路由时不自动建立别名。
- NgModule 应用可以使用基础安装能力；选择自动地图示例时明确说明首版限制。
- 地图应用模板委托官方 Angular application
  schematic 创建基础设施，固定使用 standalone、zoneless、CSS、Router、Vitest，不启用 SSR；显式传入固定选项，避免 workspace 默认设置改变已约定的模板行为。
- 新应用使用共享地图示例，空路径采用完整匹配并重定向至指定地图路径；保留完整测试和生产构建能力。新应用的 Router 和路由出口由官方生成及模板配置完成。
- 官方生成器的后续安装由外层统一调度，避免重复安装任务。skipInstall 仅控制 schematic 后续安装，库本身仍由 Angular
  CLI 处理。
- Schematics 使用独立 CommonJS 编译和局部包边界，兼容主库 ESM 发布格式。内部编译使用独立输出空间，主库打包和内部编译完成后再合并集合，避免输出清理或缓存恢复相互覆盖。
- 发布的集合使用最小 CommonJS 清单，不复制内部项目完整的私有包清单；集合、选项 schema、模板和必要编译产物完整进入组件库包。
- 现有主库构建命令、production/development 配置和发布工作流继续作为交付入口，不能只添加发布流程不会调用的 npm 后置脚本。
- 将内部项目接入根级 lint、格式化及格式检查入口；现有命令显式枚举旧项目，新增项目不能仅依赖 workspace 自动发现而遗漏检查。

## Testing Decisions

- 好的测试验证公开命令、参数、生成文件、配置变化、错误信息和最终应用行为，不断言私有辅助函数、AST 遍历顺序或内部任务拆分。
- 主要自动化边界为公开 collection。通过 SchematicTestRunner 执行编译后的集合，检查输入 workspace 到输出 Tree 的可观察变化，不新增测试专用公开接口。
- 沿用仓库 Vitest 体系，为内部项目使用独立 Node 环境；测试接入现有 pnpm
  test:lib 和完整测试入口，避免仅提供需要人工另行执行的测试套件。
- 仓库当前库测试以 Analog
  Angular 集成和 jsdom 为主，没有自有 collection 的既有测试。新增 Node 环境用于 Schematics 执行，保留现有组件测试；发布和依赖契约脚本测试可作为产物验收的先例。
- 覆盖交互确认、默认 false、显式开启与关闭、非交互行为、参数校验和跳过安装。
- 覆盖显式项目、当前目录项目、唯一应用、多应用歧义、无效项目和非应用项目。
- 覆盖缺少依赖、兼容声明保留、不兼容范围、已安装版本冲突、非 semver 声明和发布包版本要求读取。
- 覆盖样式字符串与对象形式、configuration 覆盖、去重、顺序保留及现代测试 target 的合法配置。
- 覆盖标准静态路由结构、内联与外部模板、主出口识别、缺少条件、NgModule 限制和无法分析的配置；关闭示例时不触发这些路由限制。
- 覆盖路由首位插入，包括先前存在参数路由或通配符的场景；验证自定义路径、同路径冲突、文件冲突、重复执行、修改后保留及不完整示例失败。
- 覆盖新应用默认配置、自定义应用根目录、示例名称和地图路径，以及首页完整匹配重定向。
- 生成项目的单元测试采用浅渲染验证真实模板结构，避免依赖真实 OpenLayers 浏览器初始化、瓦片网络和 jsdom 缺少的浏览器能力；不能保留与新模板不符的默认欢迎页断言。
- 以生成项目的生产构建验证真实导入与模板绑定，以浏览器验证地图显示、缩放、键盘聚焦和路由访问。
- 测试编译产物使用独立临时目录和已解析的包元数据 fixture，不要求预先存在组件库发布产物，也不以源码中的 catalog 声明冒充已发布版本范围。
- 使用实际 pnpm tarball 验证文件完整性、版本范围解析和 CommonJS factory 加载；再在临时 Angular CLI
  22.2 workspace 执行真实安装与生成流程，运行生成应用的单元测试和生产构建。
- 打包验收沿用公开 collection 和 CLI 契约，不以源码环境中的成功加载代替发布产物验证；不增加测试专用公开 API。

  build:docs，确认主库和文档没有回归。
