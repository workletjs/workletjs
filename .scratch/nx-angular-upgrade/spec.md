# Nx 23.3.0 与 Angular ~22.2.0 升级需求设计

Status: resolved

Type: task

Labels: ready-for-agent

## Problem Statement

维护者希望将工作区升级到 Nx 23.3.0 和 Angular
22.2.x，并确保组件库、文档应用、测试及发布构建继续正常运行。

仓库当前声明 Nx 23.1.0、Angular 22.0.x。现有 Analog 版本未声明支持 Angular
22，发布工作流固定的 Node 版本也低于新工具链要求。文档应用需要在保留当前 NgDoc 版本的前提下验证兼容性。仅修改主要依赖版本，无法保证整个工作区兼容。

本机已安装部分目标版本，但依赖声明和锁文件仍是旧版，因此本机安装状态不能作为升级完成的依据。

## Solution

统一升级工作区依赖声明、发布兼容范围和必要配套工具，执行经过审核的增量迁移，将 CI 切换到 Node
24，并通过现有测试、真实构建产物及文档应用冒烟检查验收。

本次暂不升级 NgDoc，五个直接依赖继续使用 `22.0.0-beta.2`，并在该版本上验证文档构建与运行。

本次保留库版本 `22.0.1`，完成可审查、可复现的升级改动；版本发布由后续流程处理。

## User Stories

1. 作为维护者，我希望所有 Nx 包统一为 23.3.0，以便避免插件与执行器版本不一致。
2. 作为维护者，我希望 Angular 开发依赖统一使用 22.2.x，以便在目标框架版本上开发和验证。
3. 作为维护者，我希望 CLI、DevKit、CDK 和 Material 同步升级，以便框架与构建工具兼容。
4. 作为组件库使用者，我希望 Angular peerDependencies 明确要求 22.2.x，以便判断应用是否满足支持条件。
5. 作为组件库使用者，我希望安装文档与发布兼容声明一致，以便正确准备依赖。
6. 作为组件库维护者，我希望 ng-packagr 与目标 Angular 版本对齐，以便生成可使用的库产物。
7. 作为测试维护者，我希望 Analog 支持 Angular 22，以便测试使用兼容的编译工具链。
8. 作为文档维护者，我希望本次保留当前 NgDoc 版本，以便缩小升级范围并独立安排后续 NgDoc 升级。
9. 作为文档维护者，我希望继续使用现有文档 builder，以便保持构建和本地开发方式。
10. 作为文档维护者，我希望工作区与文档应用解析到同一个 NgDoc 实例，以便避免重复依赖造成运行问题。
11. 作为测试维护者，我希望保留现有 Zone 初始化语义，以便升级不会改变测试运行方式。
12. 作为维护者，我希望依赖版本继续集中由 catalog 管理，以便统一维护多个 workspace 包。
13. 作为贡献者，我希望锁文件与版本声明一致，以便能够复现相同的依赖安装。
14. 作为贡献者，我希望项目明确 Node 版本要求，以便正确配置本地开发环境。
15. 作为 CI 维护者，我希望所有工作流统一使用 Node 24，以便满足完整工具链要求。
16. 作为发布维护者，我希望发布环境校验与新 Node 要求一致，以便发布构建不会使用不兼容的运行时。
17. 作为维护者，我希望迁移以仓库声明的旧版本为起点，以便不遗漏本机已经安装新版时仍需执行的迁移。
18. 作为维护者，我希望只执行本次新增迁移，以便避免重复应用历史升级操作。
19. 作为测试维护者，我希望 Vitest 配置适配新版 Nx 的加载方式，以便库和文档测试正常发现与运行。
20. 作为组件库维护者，我希望全部 secondary entry point 正常生成，以便各功能入口继续可用。
21. 作为文档维护者，我希望正式站点和 preview 构建均通过，以便两种部署路径继续可用。
22. 作为文档使用者，我希望页面、资源和地图示例正常工作，以便升级后仍能阅读和体验组件。
23. 作为审查者，我希望看到完整验证结果，以便判断升级是否满足验收标准。
24. 作为维护者，我希望库版本仍由正式发版流程管理，以便依赖升级与发版保持各自清晰的职责。

## Implementation Decisions

- 目标版本已确定：

  | 依赖组                                                    | 目标声明             |
  | --------------------------------------------------------- | -------------------- |
  | `nx` 与全部 `@nx/*`                                       | 精确 `23.3.0`        |
  | Angular Framework、CLI、DevKit、Schematics、CDK、Material | `~22.2.0`            |
  | Angular Core、CDK 的发布 peerDependencies                 | `~22.2.0`            |
  | ng-packagr                                                | `~22.2.0`            |
  | Analog Angular 插件和测试适配器                           | 精确 `2.8.0`         |
  | NgDoc app、builder、core、keywords-loaders、ui-kit        | 保留 `22.0.0-beta.2` |

- 继续使用 pnpm catalog，保留各 workspace 包的 catalog 引用，更新锁文件。
- 保留 TypeScript 6.0.3、Vite 7、Vitest 4、pnpm 10.34.5。其余依赖仅在兼容性确实要求时调整。
- 五个 NgDoc 直接依赖保持精确
  `22.0.0-beta.2`，排除在兼容性连带升级范围之外；本次不执行 NgDoc 升级迁移。
- 发布兼容范围限定为 Angular
  22.2.x；同步 README、安装指南和兼容矩阵，并明确描述升级后当前源码的要求。
- 生成 Nx 增量迁移时显式指定 23.1.0 基线，审核并替换旧迁移队列，再安装最终依赖并执行新增迁移。
- 不使用依据实际安装版本排除已应用迁移的选项，避免本机已安装 Nx 23.3.0 时漏掉待执行迁移。
- 预计新增四项 Nx 迁移；目录读取迁移应将两份 Vitest 配置改为使用 ESM 原生目录信息。实际生成结果仍需审核。
- 保留 NgDoc 的 `application` 和 `dev-server` builder，以及现有 Zone 测试初始化方式。
- 保留 NgDoc 版本带来的构建工具依赖需通过真实构建验证。如果兼容问题无法在当前范围内修复，记录问题和最小修复方案，再评审升级范围。
- 所有 CI 工作流统一使用 Node 24；根包运行时约束为
  `>=24.15.0 <25`，同步发布环境版本校验及说明，保留现有 npm 发布配置。
- 不改变组件库公开组件、输入、输出或功能行为。兼容修复若确实改变行为，必须有对应回归验证。
- 三个 workspace 包的版本均保持 `22.0.1`。

## Testing Decisions

- 测试入口和验收层级已在需求讨论中确认：以现有工作区命令为主要入口，结合真实产物检查和文档应用冒烟检查，不新增测试接口。
- 好的测试验证外部行为、安装结果和真实构建产物，不验证内部实现细节；不增加仅复述版本声明的测试。
- 更新锁文件后，`pnpm install --frozen-lockfile` 必须成功。
- `pnpm test` 必须通过，覆盖现有脚本、组件库和文档应用测试。组件测试继续沿用 Vitest、Analog
  Angular 集成和 jsdom。
- 保留现有 Node 内置测试中的 NgDoc 单实例检查：工作区与文档应用必须解析到相同的 `@ng-doc/app`。
- `pnpm lint` 与 `pnpm format:check` 必须通过。
- `pnpm build`、`pnpm build:docs` 与 `pnpm build:docs-preview`
  必须通过；文档和 preview 构建必须在保留 NgDoc `22.0.0-beta.2` 的环境中验证。
- 检查库产物的 Angular peer 范围为 `~22.2.0`，全部 secondary entry point 正常生成。
- 检查实际使用的依赖链，确认不存在不兼容的 Angular 21 构建工具。
- 启动文档应用，检查页面加载、资源路径、地图展示及基本交互。
- 兼容修复若改变公共行为，沿用现有 colocated 测试，覆盖受影响的输入、输出、生命周期清理或 OpenLayers 集成边界。

## Out of Scope

- 新功能、组件 API 调整或无关重构。
- 升级任何 NgDoc 包或执行 NgDoc 升级迁移；该升级留待后续单独安排。
- 改用 NgDoc Vite host、运行 Analog setup 生成器或切换 zoneless 测试。
- 升级 Vite、Vitest 等其他工具的主版本。
- 修改库版本、生成发版记录、发布包或部署站点。
- 清理历史迁移文档，或为普通版本升级新增 ADR、通用技术术语。
